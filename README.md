# Bug-Fixing Commit Labelling Dataset

This repository accompanies the article **"Labelling Bug-Fixing Commits with Local Open-Weight Language Models"**. It provides the datasets, scripts, prompts, and statistical analyses required to reproduce the experiments and to build new bug-fixing commit datasets using open-weight language models.

The labelling pipeline ships as two small, self-contained programs that chain together:

1. **Commit Prompt Miner** (Kotlin/Gradle) — walks a Git repository and, for every commit, produces a keyword/stemming baseline CSV and a model-agnostic prompts JSON. It makes **no** network or LLM calls.
2. **Commit Classification Prompt Executer** (Python, standard library only) — runs the mined prompts through a local open-weight model via [Ollama](https://ollama.com/) and folds the verdicts back into the same CSV, one column per model.

Because every analyzed commit references its original repository and exact commit hash, the entire benchmark is fully reconstructable from upstream Git history.

## Datasets

### `evaluation_data`

Contains the manually validated benchmark datasets used for evaluating bug-fixing commit classification.

The benchmark combines commits originating from SmartSHARK, BugsJS, BugsInPy, and PyBugHive. Each record contains the original repository, commit hash, commit metadata, and corresponding ground-truth label, allowing every analyzed commit to be reconstructed directly from its original repository.

### `released_corpus`

Contains the analysis results for **33 open-source repositories** used for large-scale evaluation. Unlike the benchmark datasets, these repositories are not manually labelled; instead, they hold the metadata and model predictions generated by the labelling pipeline. Each analyzed commit stores its original repository and commit hash, enabling full reproducibility.

## Labelling Pipeline

The complete workflow chains the two tools in this repository:

```
Repository (working tree or .git)
        │
        ▼
┌─────────────────────────────────────────────────────────────┐
│ STAGE 1 — Commit Prompt Miner  (Kotlin, no LLM calls)        │
│   Extract commit history                                     │
│   Extract commit message + git diff (JGit)                   │
│   Truncate diff   (configurable: ≤ N files, ≤ L lines/file)  │
│   Apply keyword/stemming baseline                            │
│   Construct one prompt per commit                            │
└─────────────────────────────────────────────────────────────┘
        │                                   │
        ▼                                   ▼
 <repo>-bugfixes.csv                <repo>-commit-prompts.json
 (hash, message,                    (one ready-to-run prompt
  isBugfix_stemming)                 per commit, + decode options)
        │                                   │
        │                                   ▼
        │           ┌─────────────────────────────────────────────┐
        │           │ STAGE 2 — Prompt Executer  (Python + Ollama) │
        │           │   Run each prompt on an open-weight model    │
        │           │   Parse JSON response (+ regex fallback)     │
        │           └─────────────────────────────────────────────┘
        │                                   │
        └──────────────► merged on `hash` ◄─┘
                                 │
                                 ▼
                    <repo>-bugfixes.csv  (now also holds
                    isBugfix_<model> [, reason_<model>] columns)
                                 │
                                 ▼
                    Statistical evaluation (R scripts)
```

All model inference is performed **deterministically**. The decoding parameters

- Temperature = 0
- Top-p = 0
- Top-k = 1

are embedded by the miner into each prompt's `options` block and forwarded verbatim by the executer, so labelling is reproducible across runs and machines.

## Stage 1 — Commit Prompt Miner

A standalone tool that walks a Git repository and, for every commit, produces two files:

- **`<repo>-bugfixes.csv`** — one row per commit (`hash`, `message`, `isBugfix_stemming`), where `isBugfix_stemming` is a keyword/stemming bugfix verdict derived from the commit message. This is the non-LLM baseline.
- **`<repo>-commit-prompts.json`** — one ready-to-run LLM prompt per commit (commit message plus a per-file diff summary), for classifying commits as bug fixes against *any* model later.

It makes no network or LLM calls; it only reads the repository and writes these two files. Commit messages and diffs are read with [JGit](https://www.eclipse.org/jgit/); the stemming baseline uses the `londogard/nlp` library.

### Build

Requires a JDK 23 toolchain (Gradle provisions it if missing).

```bash
cd scripts/commit-prompt-miner
./gradlew shadowJar
```

This produces a self-contained jar at `build/libs/shadow-*.jar`.

### Run

```bash
java -jar build/libs/shadow-*.jar -r <repo> -o <out-dir> [options]
```

Or directly via Gradle:

```bash
./gradlew run --args="-r <repo> -o <out-dir>"
```

### Parameters

| Flag                     | Default      | Description                                                               |
| ------------------------ | ------------ | ------------------------------------------------------------------------ |
| `--repository`, `-r`     | **required** | Git repository directory (the working tree, or one containing `.git`).   |
| `--out-dir`, `-o`        | **required** | Output directory for the CSV and prompts JSON (created if missing).      |
| `--top-files`, `-n`      | `10`         | Max changed files included per commit prompt (largest changes first).    |
| `--max-diff-lines`, `-l` | `15`         | Max diff lines per file in the prompt. `0` = only `+/-` counts, no diff. |
| `--with-reason`          | off          | Generate prompts that also ask the model for a short reason.             |
| `--hashes`               | none         | Path to a `.txt` file with one commit hash per line; mine only those.    |

> The paper's large-scale experiments used a wider diff budget than the tool defaults (≤ 10 files, ≤ 50 diff lines per file, set via `-n 10 -l 50`). The defaults above are the tool's own values and can be tuned per run.

**Implementation:** Kotlin `2.1.10` on the JVM 23 toolchain, packaged with the `com.gradleup.shadow` plugin; CLI via `clikt`, CSV via `commons-csv`. Entry point `org.anonymous.commitminer.MainKt`.

## Stage 2 — Commit Classification Prompt Executer

`scripts/commit_classification_prompt_executer.py` is the second half of the pipeline. It reads a prompts JSON produced by Stage 1, runs every prompt against the chosen model through Ollama, and folds the results into a CSV as a new `isBugfix_<model>` column group (plus `reason_<model>` if the prompts were mined `--with-reason`).

- **No third-party dependencies** — Python 3, standard library only.
- The target CSV **does not need to exist**; it is created if missing. Re-running the same model **updates its columns in place** rather than duplicating them, and writes are atomic (write-to-temp + `os.replace`).
- Recommended usage points `--csv` at the `<repo>-bugfixes.csv` from Stage 1, so the stemming baseline and every model verdict sit side by side, all keyed on the commit `hash`. (If you point it at a fresh path instead, the new CSV will contain only `hash` + the model columns.)

### Determinism and robustness

- **Deterministic decoding:** the per-prompt `options` (temperature/top-p/top-k, etc.) come straight from the mined JSON and are sent unchanged. The executer only exposes overrides for `num_predict`, `num_ctx`, and the request timeout.
- **Response parsing:** answers are parsed strict-JSON-first — including the substring between the first `{` and last `}`, to survive code fences or surrounding prose — then via a regex fallback that recovers the `bugfix` verdict (and optional `reason`) from malformed JSON. This matters for smaller models (e.g. `codegemma`, `llama3`) that frequently ignore `format: "json"`.
- **Diagnostics:** on a missing verdict, the tool prints an actionable reason to `stderr`, distinguishing an empty response, a full context window (raise `--num-ctx`), output truncated at the token cap (`done_reason="length"` → raise `--num-predict`), and a model simply not following the format.
- **Progress + ETA:** a tracker reports `Prompts i / N` with elapsed/estimated time. The clock starts on the first real prompt, so model warmup never leaks into the timing.

### Run

```bash
python3 scripts/commit_classification_prompt_executer.py \
  -p <repo>-commit-prompts.json \
  -c <repo>-bugfixes.csv \
  -m <model-tag>
```

### Parameters

| Flag                       | Default                  | Description                                                                                          |
| -------------------------- | ------------------------ | -------------------------------------------------------------------------------------------------- |
| `--prompts`, `-p`          | **required**             | Prompts JSON produced by Stage 1.                                                                   |
| `--csv`, `-c`              | **required**             | Out CSV to update (created if it does not exist).                                                   |
| `--model-version`, `-m`    | `qwen3.5:9b`             | Ollama model tag to run.                                                                            |
| `--base-url`               | `http://localhost:11434` | Ollama base URL.                                                                                    |
| `--num-predict`            | mined value              | Override the per-prompt output-token cap (raise for models truncated mid-JSON, e.g. `64`).          |
| `--num-ctx`                | mined value              | Override the context window (raise when long commit messages overflow it, e.g. `8192`).             |
| `--request-timeout`        | `120` (seconds)          | Per-prompt request timeout. Preload large models first to avoid cold-load timeouts.                 |

> **Prerequisite:** a running Ollama instance with the target model pulled (`ollama pull <model-tag>`). The executer references a warmup helper to preload big models before a long run, which sidesteps cold-load timeouts on the first request.

## End-to-End Example

Mine one repository, then label it with two different open-weight models into the same CSV:

```bash
# --- Stage 1: mine prompts + stemming baseline (no LLM calls) ---
cd scripts/commit-prompt-miner
./gradlew shadowJar
java -jar build/libs/shadow-*.jar \
  -r /path/to/some-repo \
  -o ./out \
  -n 10 -l 50
#   -> ./out/some-repo-bugfixes.csv         (hash, message, isBugfix_stemming)
#   -> ./out/some-repo-commit-prompts.json  (one prompt per commit)

# --- Stage 2: label with model A ---
python3 ../commit_classification_prompt_executer.py \
  -p ./out/some-repo-commit-prompts.json \
  -c ./out/some-repo-bugfixes.csv \
  -m qwen3.5:9b
#   adds column isBugfix_qwen3.5:9b to the same CSV

# --- Stage 2 again: label with model B (columns added side by side) ---
python3 ../commit_classification_prompt_executer.py \
  -p ./out/some-repo-commit-prompts.json \
  -c ./out/some-repo-bugfixes.csv \
  -m llama3:8b
#   adds column isBugfix_llama3:8b next to it
```

The resulting `some-repo-bugfixes.csv` is the per-commit prediction table consumed by the statistical analysis.

## Keyword/Stemming Baseline

The `isBugfix_stemming` column emitted by Stage 1 is the heuristic baseline against which the language-model labels are compared in the paper. It is derived purely from the commit message via keyword matching with stemming and requires no model and no diff, making it the cheap, reproducible reference point for the evaluation.

Every analyzed commit references its original repository and exact commit hash. Together this makes the complete benchmark fully reproducible.

## Detailed Dependencies & Runtime Environment

This section expands the **Requirements** table above with exact versions, package lists, and install commands, so the full pipeline can be reproduced end to end from this information alone.

### Operating System

All three components are platform-independent and run on 64-bit **Linux, macOS, and Windows**:

- **Stage 1 (miner)** ships both `gradlew` (Linux/macOS shells) and `gradlew.bat` (Windows); only a JVM is required on the host.
- **Stage 2 (executer)** and the **R analysis** are pure scripts with no OS-specific code.
- **Ollama** (the inference backend used by Stage 2) provides native builds for Linux, macOS, and Windows. A CUDA-capable GPU is optional but speeds up inference; CPU-only also works.
